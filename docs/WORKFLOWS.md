# Workflows and record ownership

The fictional Docent workspace demonstrates a design review of transcript access. It does not establish actual audience permissions, an authorized test method or dated operating evidence. A proposed plan stays a plan; an unanswered operating question stays incomplete.

## Record meanings

| Owner | Meaning and input | Does not establish |
| --- | --- | --- |
| Organization and AI System | Saved context, purpose and responsible-owner facts | System approval or proof of operation |
| Assessment / Review item | A scoped question, rationale, uncertainty and exact native target | An agent-issued decision or a completed operating test |
| Record | Identity, origin, version, dates, custody and location of a source or retained artifact | Relevance, sufficiency or permission to use it in a model |
| Evidence use | A claim for one exact Review, source identity/version, locator, period and limitations | A positive result merely because a link exists |
| Authored document | Editable saved wording with immutable versions and a deliberate retained-evidence action | An issued policy, supplier response or performed control test |
| Conversation / request draft | Submitted dialogue, original assistant reply and separately saved human question wording | Governance facts, an external request being sent or a decision |
| Report | A communication frozen from one saved basis | A second master or a generic full-suite assessment |
| Issued decision | Human issuer, authority basis, exact subject/scope, outcome, conditions and retained history | Authority inferred from an account, assigned role or completed form |
| Identity / grant / assignment | A technical actor, permitted scope and assigned responsibility | Delegation of approval authority or independent assurance |

The inventory owns current System facts. An Assessment captures the facts/revision being assessed, and document prose/version captures its own saved context; these are not competing editable inventory masters. The wider suite retains distinct factual, review, action and decision records. Current application commands expose only the bounded owners described here and cannot issue approvals. Existing solo/external attribution must remain intact; it must not be relabeled as authenticated colleagues' actions.

## Ordinary working path

1. Open the fictional system and its Reviews. Inspect the saved question, source context and missing operating inputs.
2. Edit context or review notes where they appear. Save deliberately; use History to inspect saved changes. Leaving an editor or closing a popup is not an approval.
3. Choose an existing source or add an original. Intake suggests a visible editable title and stable Record ID, reuses file metadata and leaves unknown facts incomplete. Technical capture time does not fill the source date.
4. Link the exact source to the intended Review. Supply the claim and any needed locator, period or limitation. The typed System/Assessment/Review relationship is checked independently. A link starts Not reviewed / Not checked.
5. Where a document helps, choose a supported deterministic template, inspect the reused facts, complete missing wording and Save. Retain a specific saved version as evidence only through the explicit action. Later edits do not rewrite that retained version.
6. For the focused transcript-access brief, generate from saved work. Reopen/download the exact retained version or inspect older versions when its basis is no longer current.

Optional AI can draft evidence questions for the admitted fictional task. In chat, inspect the reply and its sources, edit useful questions and choose Save request draft. The older fixed-task action instead offers Use in request draft followed by the editor's Save. Uploading or saving a document does not admit it to the provider context.

## Exceptions and recovery

- Duplicate original bytes reuse their known identity rather than creating another upload. Different bytes need a distinct identity. A predecessor may be selected explicitly; a matching filename does not establish a version relationship.
- An unsaved editor remains separate from a saved record. A conflict keeps the user's text available for reconciliation; retry an uncertain operation with its original operation ID and unchanged payload.
- Evidence-use removal is soft and restorable. Earlier captures, exact original bytes and history remain distinct from current metadata. A link cannot silently move to another Review.
- Failed, stopped or unconfirmed AI work stays visible as such. It cannot silently apply a late result. A reply with a valid structure still needs human inspection for unsupported content.
- Failed or interrupted PDF work keeps earlier reports and saved work. A restart reconciles pending technical jobs rather than calling them completed.

## Source mapping and extension rule

The suite is the upstream source for field meaning and responsibility. Code metadata records exact versions, labels and locators; the fictional seed is only test/example data. For example, current Record intake maps to the governance register's Records fields, Review/Evidence use maps to the assessment workbook's Review and Evidence sheets, and document schemas map to their owning manual/procedures. See [source provenance](SOURCES_AND_RIGHTS.md).

Before extending a workflow, inspect the actual owning suite source and its upstream/downstream dependencies. Verify the purpose, ownership, conditionality and reuse of each field or step. Separate externally verified obligations, adopted internal rules, optional template choices and software patterns. Do not treat a field count, passing construction test or template inclusion as proof that every field is required. Propose source corrections separately; application work does not authorize edits to controlled source bodies.

The next team connection must preserve these meanings while adding attributed actions and complete access checks. It must not create a second assessment, duplicate Action or automatic decision merely to populate a person's work list.
